# 从用户需求到独立客户端的补充实施方案

2026-11-22。基线为 `dsh-self@239dae0`、OctoDeEpSeeK 模板 `48f3f019`、官方 dsh `0.2.2-rc.5`。首个交付平台是 Windows x64。基础目标、原有里程碑和上游引用分别见[总方案](implementation-plan.md)、[参考项目与文档](references.md)和[模板来源](../UPSTREAM_SOURCE.md)。

## 用户交付条件

| 用户任务 | 可观察的通过条件 |
| --- | --- |
| 说需求、发设计稿或参考页 | 识别用户任务和素材用途。无足够信息时询问一条会改变方案的问题。单独上传图片也能继续。支持的动作、尚缺的动作、需要连接的服务分别说明。 |
| 挑选和修改方案 | 每个必需动作展示能交付的实现或明确的缺口。展示选择理由、替代项、插件版本和本机状态。不同的参考稿能影响结果。用户明确修改的颜色、布局或顺序优先。 |
| 验证自己的产品 | 用户可带自己的文件试操作、读到结果并重开。正式试用加载同一份修订、同一插件锁、相同首页和宿主业务处理。草图只提供外观参考。 |
| 生成、独立使用与升级 | 作者通过 Studio 得到可安装文件和可复算回执。退出 Studio 后，接收者能在无开发工具的电脑安装、使用、重启恢复。改名升级后资料可找回，同机两款产品同时工作。 |

## 实施顺序与完成判据

| 顺序 | 实现位置及最小改动 | 验收与失败行为 |
| --- | --- | --- |
| 1. 导出结果可信 | 在 Studio 原有导出路径上区分原生安装包、跨平台配方、失败。移除配置 JSON 冒充安装包的分支。用同一次修订的规格和目标锁做独立校验，对缺少的必需动作给出具体名称。复用构建器回执，核对目标、身份、版本、哈希、大小和实际文件类型。保留失败原因并允许重试。 | 缺工具链、缺必需动作、缺文件或回执错误均不会生成成功发布记录。正常 Windows 构建可下载真实 NSIS，复算摘要相符。已有配置、已安装成品和历史配方继续可读。 |
| 2. 插件选择影响运行 | 对内置投标和设计适配器，复用现有产品壳与适配器实现，按实际锁启用处理器和首页入口。将决定运行行为的锁内容写入种子。第三方候选从已验证的本地包物料组装，保存包字节和传递依赖的完整性，据此生成启用清单。缺物料的候选显示缺口或替代项。 | 同修订加减插件会改变种子摘要和运行时可用动作。桌面读取的锁与构建回执一致。必需能力不可交付时带原因回到选型。可选能力的取舍明确展示。 |
| 3. 需求与素材进入方案 | 在现有蓝图生成前归一化用户文本、网页标题/分区/主题和图稿输入。闭集目录内按实际动作选型，目录外明确指出覆盖边界。图稿原件按项目保存。区分参考视觉与业务作品，只将用户选作业务作品的素材带入成品。配色、分区、布局的来源可追踪。复用现有本地提色。有可用视觉模型再提取闭集布局，离线时让用户确认。 | 库存盘点不会收到投标方案。相同需求配不同图，差异可见或说明需要确认的地方。仅发图可继续操作。同一作品经保存、重开和导出后可回读，普通编辑修订保留附件。 |
| 4. 两条业务链和真实预览 | 成品首页调用现有 DOCX 与设计适配器。投标链为导入、显示截止日/评分/材料、导出并重开响应表。设计链为导入原图、生成代理、保存坐标、重开批注、导出 PNG。使用同一产品壳、处理器与项目 ID，在独立数据目录启动正式试用。快速样例标明来源。 | 用户通过按钮完成两套业务，无模型凭据时本地能力可用。预览和安装版都使用一份新的用户文件，回读导出的实际内容、批注坐标和保存状态。从已验修订构建，修订变化能被发现。 |
| 5. 普通作者取得工具链，Windows 验收 | 复用现有 base-shell、builder CLI 和 NSIS。开发可显式指定本机工具路径，发行提供定版的离线工具包和校验清单，通过 Studio 发现或引导导入。把测试用的 dsh、产品工作区、Studio 数据指向隔离目录。安装测试使用独立测试用户或受控环境。 | 从分发的 Studio 插件开始，作者在无开发工具的机器导出，接收者安装。两产品同时打开并写入不同文件，关掉 Studio，重启与升级后各自读回。分别记录启动到可操作、构建、产物和种子大小。按总方案的 320 MB、15 s/4 s、60 s 目标报告样本和 P95。 |
| 6. 后续平台 | 复用上述产品和动作契约，在原生 Linux 与 macOS 上完成封装和同一组业务验收。签名分发根据实际证书和发布渠道另行验收。 | 跨平台配方、分阶段清单、已构建原生包、已安装验收各有明确状态。 |

## 交付和复核

两位评审者分别从用户操作和构建实现复核了基线，并交换意见。双方均要求把每次构建的规格、锁及已装入规格的品牌素材冻结到任务目录。界面把运行中的任务更新到最终结果。正式试用应复用已有 `PreviewReportSchema` 的修订和摘要，外观草图可供随时参考。产品侧提出用两个同名、不同内容的业务文件验证独立保存与重开。工程侧确认现有内置适配器已经编入产品壳，先按可执行动作启用 Host 与界面，避免再做一套插件安装系统。

首批以 Windows 本地投标流程验证交付语义和可操作性，使用已有 CLI、文件格式、适配器和 NSIS。用户在 Studio 产生可复核结果、改名、重试，开发机使用现有工具链验证。设计工作流和第三方物料依赖第一条可运行流程。无开发工具作者的离线分发、同时安装升级及 P95 另做实机验收，保留各自证据。

| 证据 | 核验方式 |
| --- | --- |
| 开发机 | 从 Studio 正常入口保存需求、试用、出包。记录构建修订和锁、插件加载结果、真实输出及校验值。测试输入目录不得枚举个人 dsh 配置。 |
| 缺依赖与失败 | 正常的不可满足需求、未装工具链、受损产物、重新生成和旧项目重开各有回归用例。 |
| 发布前 | 在独立普通用户环境做安装、并发使用和升级。样例冒烟、组件测试、开发机实包、干净机验收各自标注。性能从启动至首页可操作计时。 |

实施中按本地源码跟踪[需求和构建服务](../packages/dsh-self-studio/src/host/studio-service.ts)、[规划器](../packages/dsh-self-studio/src/host/extractor.ts)、[选型器](../packages/catalog/src/resolver.ts)、[种子生成](../tools/builder/src/seed-builder.ts)、[成品首页](../templates/desktop/plugins/dsh-shell-product/src/client.tsx)及[Windows 验收](../scripts/verify-win-e2e.mjs)。依赖完整性核对采用 npm 的包记录语义。桌面验收应驱动实际窗口并读取操作结果。[npm 锁文件文档](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/) · [Electron 自动化测试指南](https://www.electronjs.org/docs/latest/tutorial/automated-testing)

### 本地复核入口

在候选源码根执行。示例默认 OctoDeEpSeeK 与工程同处一个父目录。独立检出时，`DSH_SELF_ELECTRON_DIST` 指向 OctoDeEpSeeK 的 `apps/desktop/node_modules/electron/dist`，`DSH_SELF_RUNTIME_NM` 指向 `apps/desktop/runtime/node_modules`。在已按锁文件安装依赖的检出目录中，`build` 先生成插件、成品前端和构建 CLI。基础壳放在独立的开发目录，便于复用。作者测试从隔离配置启动官方 dsh 并进入 Studio，业务测试直接驱动 Electron 窗口。后一个脚本也接受下载的 NSIS 安装包或已提取的品牌 EXE 作为参数。传入安装包时，脚本解开实际载荷，启动其中的程序，再检查业务输出。

```powershell
node scripts/build.mjs
node scripts/assemble-base-shell.mjs studio-workspace-release
$env:DSH_SELF_BASE_SHELL_DIR = (Resolve-Path '.dev/studio-workspace-release/win32-x64').Path
$env:DSH_SELF_ACCEPTANCE_DIR = Join-Path $PWD ('.dev/verify-' + [guid]::NewGuid().ToString('N'))
node scripts/verify-studio-windows.mjs
if ($LASTEXITCODE -ne 0) { throw '作者流程未通过' }
$result = Get-ChildItem "$env:DSH_SELF_ACCEPTANCE_DIR/author-*/result.json" |
  ForEach-Object { Get-Content -Raw -LiteralPath $_.FullName | ConvertFrom-Json }
node scripts/verify-product-workspace.mjs $result.job.installer
```

两个验收脚本默认把每次执行保存在 `.dev/studio-acceptance` 下的新目录。跨工作树集中收集样本时，可以给两者设置同一个 `DSH_SELF_ACCEPTANCE_DIR`。作者测试会存档本轮实际使用的插件包及其 SHA-256。

当前作者工具链可在 dsh 插件配置中指定 `builderCliPath`、`baseShellDir`。已有开发环境也可通过 `DSH_SELF_BUILDER_CLI`、`DSH_SELF_BASE_SHELL_DIR` 指向同一套工具。项目自带的 `demo:dsh` 读取这两个设置。打包和测试入口见[根脚本](../package.json)、[官方 dsh 作者界面验收](../scripts/verify-studio-windows.mjs)与[成品业务验收](../scripts/verify-product-workspace.mjs)。

## 剩余工作及进入下一阶段的判据

1. **普通作者的离线工具包。** 汇集已验证版本的 Windows 基础壳、Node、构建 CLI 及其生产依赖，带上实际使用的 NSIS 和 7-Zip 物料与摘要。Studio 提供发现或导入入口。通过条件为一台无 Node、无项目源码的标准用户机器安装 Studio 后能从界面创建成品。接收成品的另一台机器独立安装并操作本地文件。按首包与后续包分别计时，再决定是否缓存公共压缩内容。当前日历功能可导出按日事件，精确到时分的提醒需要追加带时间的标书和日历应用的读回验收。
2. **图稿与工作流的表达能力。** 对标明为业务作品的原件，随修订生成受控素材清单，打包时验证摘要，成品首次打开即可选择该图，升级后不覆盖批注。对于工作台参考稿，提取候选分区、顺序和组件边界，展示来源并允许用户纠正。先用两张同色、不同布局的图和一张长图验证。需要语音时接入宿主已有转写能力，并让作者确认转写文本。
3. **复合办公需求与第一项外部业务。** 以“处理标书、查公开标讯、收邮件、走审批”为验收输入，先让用户确认逐项能力清单，列明本地可用、缺少插件、需要连接的部分。目前实测范围是本地标书与设计批注。再从首批用户最需要的未覆盖动作里选一个，例如查询公开标讯。固定可用插件、版本、许可证、传递依赖和连接条件，装入单个试验产品。在干净接收机上验证真实查询、无凭据时的提示及可选功能退出路径，再把它标为可交付。后续插件按这个证据扩充目录。
4. **把品牌覆盖到桌面外壳。** 实测的产品首页、业务工作区和 Windows 可执行文件已经使用产品身份，侧栏左上仍显示 DeepSeek Harness。沿用 OctoDeEpSeeK 已验证的 `sidebar.brand.mark`、`sidebar.brand.name` 和 `conversation.hero.brand.mark` 插槽，从同一产品规格读取名称、图标和浅深色。用两个不同品牌核对启动后的侧栏、会话首页和桌面快捷方式，并保留各自的数据。[OctoDeEpSeeK 品牌插槽实现](../../OctoDEepSeeK/packages/dsh-shell-octo/src/client.tsx)
5. **安装、升级与平台。** 在隔离 Windows 用户上同时启动两款正式安装的产品，写入不同数据，关闭 Studio，重启并执行改名升级及单独卸载。按总方案采集 P95。macOS 与 Linux 各在原生系统重复安装和业务回读。当前下载的配方只能证明已生成构建输入。
